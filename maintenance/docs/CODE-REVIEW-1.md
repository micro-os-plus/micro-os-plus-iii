## How the Cortex-M port drives the core

The facts below, from the port's `src/rtos/os-core.cpp` and
`include/cmsis-plus/rtos/port/os-inlines.h`, are the ones the findings
depend on.

- **Interrupt state.** `port::scheduler::initialize()` only calls
  `__disable_irq()`. The default `main()` calls `scheduler::initialize()`
  (`src/rtos/os-main.cpp:146`), so in 7.0.0 interrupts were already
  masked from that point until the scheduler starts.
  `port::scheduler::start()` is the only place that enables them again
  (`__set_BASEPRI(0)`, then `__enable_irq()`).
- **SysTick.** The port starts SysTick in `port::clock_systick::start()`,
  which the core calls from `scheduler::start()`. The core's default
  `SysTick_Handler` is an empty weak function; platforms that need the
  tick provide their own.
- **Rescheduling.** `port::scheduler::reschedule()` only pends PendSV.
  It does nothing when the scheduler is locked, or when it is called in
  handler mode while preemption is disabled. PendSV has the lowest
  priority, so the switch happens when the last interrupt returns.
- **Context switch.** `PendSV_Handler` saves the registers and calls
  `switch_stacks()`, which masks interrupts and calls the core's
  `internal_switch_threads()`. That function relinks the outgoing
  thread through `internal_relink_running_()` (only if its state is
  `running`), then takes the head of the ready list. A thread whose
  state is not `running` at that point is not put back in the ready
  list; only a later `resume()` can bring it back.
- **Critical sections.** `interrupts::critical_section` uses PRIMASK,
  or BASEPRI when `OS_INTEGER_RTOS_CRITICAL_SECTION_INTERRUPT_PRIORITY`
  is defined.
- **Port-delegated objects.** The Cortex-M port does not implement any
  `OS_USE_RTOS_PORT_*` object; those branches are used only by other
  ports, such as FreeRTOS.
- **SMP.** The port has an `OS_USE_SMP_SCHEDULER` mode (1 CPU on
  generic Cortex-M, 2 CPUs on the RP2350). It needs the kernel from the
  `smp` branch (or `micro-os-plus-iii-smp`); this branch has no SMP
  code. Some changes under review (`resume()` in #1, the reaper wait in
  #2) appear to have been ported back from the SMP work, where their
  assumptions differ.
- **Packaged version.** The packaged 1.1.0, used by the tests, is the
  sibling repository without the `OS_USE_SMP_SCHEDULER` additions; the
  non-SMP code paths above are the same in both.

## How the POSIX port drives the core

The tests link the packaged `micro-os-plus-iii-posix-arch` 1.0.1, which
is the original single-CPU port. The sibling repository has since been
rewritten as an SMP port (each host thread acts as a CPU, with a spin
lock as the kernel lock), written for the `smp` branch kernel. The
facts below are from the packaged 1.0.1, with the SMP rewrite noted
where it differs.

- **Preemption.** The port is **non-preemptive** (its greeting says
  so). `port::scheduler::reschedule()` returns immediately when the
  scheduler is locked **or** when called in handler mode (from the tick
  signal handler), whatever `scheduler::preemptive()` says. Threads
  switch only when thread-mode code calls `reschedule()`: `yield()`,
  blocking calls, or `resume()` from another thread.
- **Handler mode.** `in_handler_mode()` is `signal_nesting > 0`; the
  tick signal handler increments it around `os_systick_handler()`.
- **Context switch.** `reschedule()` calls the core's
  `internal_switch_threads()` inside an interrupts critical section
  (the tick signal blocked), then `swapcontext()`. As on Cortex-M, only
  a `running` outgoing thread is relinked.
- **Scheduler lock.** `locked(state)` starts with
  `os_assert_throw(!interrupts::in_handler_mode(), EPERM)`, as on
  Cortex-M.
- **Idle.** `wait_for_interrupt()` is `pause()`, which returns after the
  next signal is handled.
- **Startup.** The core's `src/startup/` is `__ARM_EABI__` only; the
  POSIX port does not use `Reset_Handler` or the hardware hooks
  (the SMP rewrite calls the two hooks from `scheduler::initialize()`).
- **SMP rewrite.** In the sibling version, `reschedule()` from handler
  mode defers the switch to the handler exit instead of dropping it, and
  each CPU can call `flags_raise()`, `resume()` and the clock lists
  concurrently.

## #1 - Lost wake-up: `resume()` ignores running threads

**File:** `src/rtos/os-thread.cpp:684`

### Problem

`thread::resume()` now links a thread into the ready list only when its
state is `suspended` or `initializing`. Before the change, a `running`
thread was also linked (the test was `ready_node_.next() == nullptr`).

`internal_flags_wait_()` depends on the old behaviour. It checks the
flags in one critical section and calls `internal_suspend_()` in
another, so there is a window between the two.

### Scenario

1. Thread T calls `flags_wait(0x1)`, finds no flags, and leaves the
   critical section.
2. An ISR calls `T.flags_raise(0x1)`. The flag is set, but `resume()`
   does nothing because T is still `running`.
3. T calls `internal_suspend_()`, which sets `suspended` and
   reschedules.
4. The flag stays raised, but T is never woken.

The same race exists between `thread::interrupt()` and
`this_thread::suspend()`.

### Documentation and tests

- The user's manual (thread event flags) says: "any other thread or ISR
  can raise any set of flags, at any time" and "If the thread was
  suspended and waits for flags, it is resumed." Raising flags from an
  ISR is therefore the documented use case, which is exactly the
  scenario above.
- The reference documents `thread::resume()` as "Internal, used in the
  implementation of synchronisation objects", usable from ISRs.
- The tests never exercise the race: every flags test in `rtos-apis`
  and `instrumentation` raises the flags on the current thread
  **before** waiting.

### Port behaviour

- On Cortex-M, `internal_suspend_()` sets `suspended` and calls
  `reschedule()`, which pends PendSV. In `switch_stacks()`,
  `internal_relink_running_()` skips the thread because it is no
  longer `running`, so nothing puts it back in the ready list. The
  scenario above is therefore what happens on the port.
- The comment in `resume()` explains the change: "In SMP, a running
  thread has `ready_node_.next() == nullptr`; it must not be
  re-enqueued while actively executing." On SMP that rule is
  necessary, since another CPU could pick the thread from the ready
  list. However, this branch has no SMP code, and the flags wait was
  not changed to match.
- The `smp` branch has the same `resume()`, `internal_suspend_()` and
  flags wait, so it has the same lost wake-up.
- On POSIX 1.0.1, the tick signal can arrive between the check and the
  suspend; a timer callback that raises the flags then hits the same
  no-op `resume()`. In the SMP rewrite of the POSIX port, another CPU
  can raise the flags at any moment, which makes the window much easier
  to hit.

### Suggested fix

The preferred option, safe for both one CPU and SMP, is to make the
check and the suspend atomic: in `internal_flags_wait_()` (and the
timed variant), set `state_ = state::suspended` inside the same
interrupts critical section that found the flags not raised, then call
`reschedule()` after leaving it. A `resume()` from an ISR in the window
then sees `suspended` and links the thread. Do the same in
`this_thread::suspend()` for `thread::interrupt()`.

Reverting `resume()` to link a `running` thread (the old
`ready_node_.next() == nullptr` test) also fixes it on one CPU, but
reintroduces the problem the change was made for on SMP.

## #2 - `kill()` livelocks yielding to the lower-priority idle thread

**File:** `src/rtos/os-thread.cpp:1428`

### Problem

`thread::kill()` (and therefore `~thread()`) can spin forever if the
idle thread has already set the target to `destroying` but has not yet
finished `internal_destroy_()`.

In that case the new branch loops on `this_thread::yield()` until the
state becomes `destroyed`. However, `yield()` only gives the CPU to
threads of equal or higher priority. The idle thread has the lowest
priority, so it never runs again and never finishes the destruction.

### Scenario

1. Thread A (normal priority) exits and goes on the terminated list.
2. Idle sets `A.state_ = destroying` and is preempted inside
   `internal_destroy_()`, for example by a tick that wakes thread B.
3. B calls `delete a_thread` or `a.kill()`. `we_claimed` is false, so B
   loops on `yield()`.
4. Idle never gets the CPU, so `destroyed` is never set. The result is a
   livelock at 100% CPU.

### Documentation and tests

- The user's manual (threads, "Destroying threads") says that when a
  thread is needed for immediate reuse, the parent should call
  `thread::kill()`, "which will destroy the thread on the spot". The
  documented contract is therefore that `kill()` finishes the
  destruction itself, not that it waits for idle.
- The manual also says that a self-terminated thread "adds itself to a
  list that will be later processed by the idle thread".
- The reference says `~thread()` calls `kill()` if the thread is not
  already destroyed, and documents the `destroyed` state as "Terminated
  and resources (like stack) released".
- No test calls `kill()` explicitly or destroys a thread while idle is
  processing the terminated list.

### Port behaviour

- `os_rtos_idle_actions()` (`src/rtos/os-idle.cpp:68`) sets
  `destroying` inside an interrupts critical section, then calls
  `internal_destroy_()` **without** locking the scheduler. Idle can
  therefore be preempted half-way through, which is the window in the
  scenario.
- On Cortex-M, `yield()` ends in a PendSV switch that takes the head of
  the ready list, which is the highest-priority ready thread. Idle has
  `priority::idle` (or lower with
  `OS_BOOL_RTOS_THREAD_IDLE_PRIORITY_BELOW_IDLE`), so a normal-priority
  killer never yields to it.
- On SMP with two CPUs (RP2350), the other CPU's idle thread could
  finish the destruction, which may be why the loop was written this
  way. On one CPU, which is every configuration of this branch, it
  livelocks.
- On POSIX 1.0.1, which is non-preemptive, the tick cannot switch away
  from idle half-way through `internal_destroy_()`, and the mutex
  unlocks it performs run under a scheduler lock, so the window does
  not open there. The problem is specific to preemptive ports
  (Cortex-M, and the SMP rewrite of the POSIX port).

### Suggested fix

The preferred option, consistent with the documented "on the spot"
semantics, is to let the killer finish the destruction itself instead
of waiting for idle (for example, take the target off the terminated
list under the critical section and complete `internal_destroy_()` in
the caller).

The alternative is to block on a real wake-up instead of polling (for
example a join-style wait that `internal_destroy_()` signals).

## #3 - Condition variable wait error path leaves the thread `suspended`

**File:** `src/rtos/os-condvar.cpp:621` (and line 813 in `timed_wait()`)

### Problem

In `condition_variable::wait()` and `timed_wait()`,
`internal_link_node()` sets the current thread state to `suspended`
before the mutex is unlocked. If `mutex.unlock()` fails, the error path
unlinks the node but does not restore the state to `running`.

The thread therefore keeps running while marked `suspended`.
`internal_relink_running_()` relinks only `running` threads, so at the
next preemption the thread is not put back in the ready list.

### Scenario

1. A thread calls `cv.wait(mx)` without owning `mx` (or on an
   error-checking or not-recoverable mutex), so `unlock()` returns
   `EPERM`.
2. `wait()` returns `EPERM` with `state_ == suspended`.
3. At the next tick or yield, `internal_switch_threads()` does not
   relink the thread. It disappears from scheduling until something
   calls `resume()` on it.

### Documentation and tests

- The reference documents this error path explicitly: `wait()` and
  `timed_wait()` return `EPERM` when the mutex "type is
  `mutex::type::errorcheck` or the mutex is a robust mutex, and the
  current thread does not own the mutex". `ENOTRECOVERABLE` and
  `EOWNERDEAD` are also documented. So the failing path is a
  documented, expected outcome, not only a programming error.
- The tests do not cover it: condition variables are only constructed,
  signalled and broadcast; `wait()` runs only under `extra` in the ISO
  test, and `os_condvar_wait()` is still marked `// TODO` in
  `test-c-api.c:807`.

### Port behaviour

On Cortex-M, the next PendSV calls `internal_relink_running_()`, which
relinks the outgoing thread only if its state is `running`. A thread
left in `suspended` is switched out and not relinked, as described in
the scenario.

On POSIX 1.0.1 the same happens at the thread's next `yield()` or
blocking call, since `reschedule()` uses the same
`internal_switch_threads()`.

### Suggested fix

Either:

- in the error path, also set `crt_thread.state_ = state::running`
  inside the interrupts critical section; or
- unlock the mutex before linking the node (keeping the ordering safe
  against lost signals).

## #4 - `timed_wait()` reports a timeout for signalled waits

**File:** `src/rtos/os-condvar.cpp:831`

### Problem

`timed_wait()` decides whether the wait timed out by testing
`steady_now() >= timeout_timestamp` **after** `mutex.lock()` returns,
not by checking what actually woke the thread. If re-acquiring the
mutex takes until after the deadline, a wait that was signalled is
reported as `ETIMEDOUT`.

The new `estd::condition_variable::wait_for()`
(`include/cmsis-plus/estd/condition_variable:301`) says it "trusts the
kernel's verdict" to avoid exactly this, but the kernel verdict is
itself unreliable, so the signal is still reported as
`cv_status::timeout`.

### Scenario

1. A thread calls `cv.timed_wait(mx, 10)`.
2. At tick 9, another thread calls `signal()`.
3. `mx` is held by a third thread until tick 15.
4. `mutex.lock()` returns at tick 15, `steady_now() >= ts` is true, and
   the caller gets `ETIMEDOUT` (or `cv_status::timeout`) for a signal it
   has consumed.

### Documentation and tests

- The reference documents `ETIMEDOUT` only as "The timeout has
  passed.", which the current code literally satisfies. It does not say
  whether a signalled wait may report a timeout.
- Code that waits in a predicate loop (the correct usage, and what the
  predicate overloads of `estd::condition_variable` do) re-checks the
  condition and is not affected. Code that relies on the status alone,
  or a `signal()` aimed at a single waiter, can lose the notification.
- `timed_wait()` on a condition variable is not called by any test.

This is why the severity was lowered to **minor**.

### Suggested fix

Before re-locking the mutex, record which path woke the thread. For
example, check whether the clock removed `timeout_node` while `node`
was still linked (timeout), or `signal()` removed `node` (signalled).
Base the return value on that, not on the time after the lock.

Alternatively, keep the current behaviour and correct the comment in
`estd::condition_variable::wait_for()`, documenting that a timeout may
be reported for a wait that was signalled close to the deadline.

## #5 - Idle does not yield when exactly one thread is ready

**File:** `src/rtos/os-idle.cpp:193`

### Problem

With `OS_INCLUDE_INSTRUMENTATION`, the idle thread yields only when
`ready_threads_list_.head() != ready_threads_list_.tail()`, that is,
when two or more threads are ready. The running idle thread is not in
`ready_threads_list_`, so with exactly one ready thread `head() ==
tail()` and idle does not yield.

### Scenario

1. The scheduler is non-preemptive (`scheduler::preemptive(false)`).
2. While idle runs, an ISR resumes one thread. The `reschedule()` call
   from the ISR does nothing in handler mode.
3. Idle sees `head() == tail()` and keeps looping without yielding.
4. The woken thread never runs. The system stays in idle until a second
   thread becomes ready.

### Documentation and tests

- The user's manual (basic concepts) says µOS++ "implements both
  cooperative and preemptive multi-tasking", and that in cooperative
  mode an ISR-resumed thread may not run "until the low priority thread
  decides to yield". Idle is that low-priority thread, so it must
  yield when anything is ready.
- `scheduler::preemptive(bool)` is part of the public API (reference:
  "Set the scheduler preemptive mode.").
- The only test sets `scheduler::preemptive(false)` and immediately
  back to `true` (`test-cpp-api.cpp:1206`), so cooperative mode is
  never exercised.

### Port behaviour

- On Cortex-M, `port::scheduler::reschedule()` returns without pending
  PendSV when it is called in handler mode and preemption is disabled.
  The ISR's `resume()` therefore does not switch, and only a `yield()`
  from the running thread (idle) can start the woken thread.
- With `wait_for_interrupt()` (WFI) enabled, idle wakes up after the
  interrupt, sees one ready thread, does not yield, and goes back to
  sleep. The woken thread waits for an unrelated event.
- 7.0.0 always called `yield()` here; the condition is new in this
  change.
- **On POSIX 1.0.1 this is not limited to cooperative mode.** That port
  never switches from the tick handler, so a thread woken by a timeout
  (`sleep_for()`, a timed wait) or by a timer callback runs only when
  the running thread yields. When all threads are blocked and idle is
  running, idle's `yield()` is the only way the woken thread can start.
  With `OS_INCLUDE_INSTRUMENTATION` on the native platform, the first
  time exactly one thread wakes up while the others are blocked, idle
  loops in `pause()` forever. The native and QEMU test configurations
  do not define `OS_INCLUDE_INSTRUMENTATION` (only `nucleo-f411re`
  does), so the tests cannot show it.

### Suggested fix

Test `!ready_threads_list_.empty()` instead of `head() != tail()`.

## #6 - Port event flags branch calls an undeclared function

**File:** `src/rtos/os-evflags.cpp:598`

**Status:** fixed (not committed).

### Problem

The `OS_USE_RTOS_PORT_EVENT_FLAGS` branch of `event_flags::raise()`
calls `instrumentation::event_flags::raised(this, mask, res)`.
`include/cmsis-plus/diag/instrumentation.h` declares no such function;
it only declares `raise_retval(evflags, res)`, which the non-port branch
already uses. The call was added in `2cbd20a0` ("add event_flags
instrumentation").

A smaller, related issue is in the port branches of both `raise()` and
`clear()`: `os_assert_err (mask != 0, EINVAL)` comes after the
instrumentation entry call. With `NDEBUG` it returns `EINVAL` straight
away, so the instrumentation records an entry (`raise`, `clear`) with no
matching exit (`raise_retval`, `clear_retval`). The non-port branches
don't have this problem: the mask check is inside
`internal::event_flags::raise()`/`clear()`, so `EINVAL` comes back in
`res` and still goes through the exit call.

### Scenario

An application that defines `OS_USE_RTOS_PORT_EVENT_FLAGS` fails to
compile:

```text
'raised' is not a member of 'os::instrumentation::event_flags'
```

### Documentation and tests

- Every test application's `os-app-config.h` defines
  `OS_USE_RTOS_PORT_EVENT_FLAGS`, but only inside
  `#if defined(USE_FREERTOS)`, which no configuration sets. The branch
  is therefore never compiled by the tests, which is why the error went
  unnoticed.
- Neither the user's manual nor the reference mentions the
  `OS_USE_RTOS_PORT_*` options.
- Neither the Cortex-M nor (as far as these headers show) the POSIX
  port implements port-delegated event flags; only a FreeRTOS-style
  port would compile this branch.

### Fix applied

In the port branches of `event_flags::raise()` and
`event_flags::clear()` in `src/rtos/os-evflags.cpp`:

- `raise()` now calls `instrumentation::event_flags::raise_retval()`, as
  the non-port branch does.
- The `os_assert_err()` early return is replaced by an `assert()` plus a
  conditional call, so every return goes through the instrumentation
  exit call. Debug builds still assert; `NDEBUG` builds still return
  `EINVAL`.

```cpp
#if defined(OS_USE_RTOS_PORT_EVENT_FLAGS)

      // Validate here rather than with os_assert_err(), which would
      // return early and skip the instrumentation exit call.
      assert (mask != 0);

      result_t res = EINVAL;
      if (mask != 0)
        {
          res = port::event_flags::raise (this, mask, oflags);
        }

      instrumentation::event_flags::raise_retval (this, res);
      return res;
```

`clear()` has the same shape, calling `port::event_flags::clear()` and
`clear_retval()`.

### Verification

No port implements delegated event flags, so the branch was compiled
with `-fsyntax-only` against a stub `port::event_flags` class (static
template functions) and a stub `os_evflags_port_data_t`. The compiler
command came from the `native-cmake-clang-debug` build (`-Weverything
-Werror`), with `-DOS_USE_RTOS_PORT_EVENT_FLAGS` added:

- The original file fails with
  `no member named 'raised' in namespace 'os::instrumentation::event_flags'`.
- The fixed file compiles without warnings in both debug and `NDEBUG`
  builds.
- Builds with `OS_INCLUDE_INSTRUMENTATION` enabled could not be checked
  this way, because they need the SystemView header
  (`instrumentation-sysview-micro-os-plus-iii.h`). The fix only uses
  functions that are declared in the instrumentation header both with
  and without instrumentation.

The default (non-port) branches are unchanged.

### Follow-up

To catch this class of error, consider a build-only test configuration
that defines the `OS_USE_RTOS_PORT_*` macros together with a stub port,
as in the verification above.

## #7 - `realloc()` copies 0 bytes when the usable size is unknown

**File:** `src/libc/stdlib/malloc.cpp:315`

### Problem

`realloc()` now copies `min(bytes, usable_size(old))` bytes. The base
`memory_resource::do_usable_size()` returns 0 to mean "unknown", and
only `first_fit_top` (and `lifo`, which derives from it) overrides it.
For any other resource, the copy size is 0, so the new block gets none
of the old contents, while the old block is freed.

### Scenario

1. `OS_TYPE_APPLICATION_MEMORY_RESOURCE` names a resource that does not
   derive from `first_fit_top`, or the application calls
   `estd::pmr::set_default_resource()` with one.
2. The application runs:

   ```c
   char* p = malloc (16);
   strcpy (p, "hello");
   p = realloc (p, 32);
   ```

3. `p` now holds uninitialised data: the contents are lost without any
   error.

### Documentation and tests

- The 7.0.0 listing shown in the reference copies `bytes` (the new
  size) unconditionally, which reads past the end of the old block on
  every growing `realloc()`. The change correctly fixes that over-read
  for the default resource.
- `malloc.cpp` is compiled only for `__ARM_EABI__`, and the default
  application resource is `first_fit_top`
  (`src/startup/initialise-free-store.cpp:42`), so the default
  configuration is **not** affected. Only custom application resources
  are.
- `usable_size()` / `do_usable_size()` are not documented in the
  reference (7.0.0) or the user's manual, which still lists memory
  allocators as TODO.
- No test calls `realloc()`.

This is why the severity was changed to **narrow**.

### Suggested fix

When `usable_size()` returns 0, fall back to copying `bytes` (the 7.0.0
behaviour) for that case only, and keep the `min()` when the size is
known. Also document `usable_size()` and `do_usable_size()`, including
the meaning of 0, so that custom resources know to implement it.

A more complete option is to implement `do_usable_size()` in every
shipped resource that can be the default (`block_pool`,
`malloc_memory_resource`, `new_delete_memory_resource`), and keep the
fallback only for third-party resources.

## #8 - `Reset_Handler` masks interrupts until the scheduler starts

**File:** `src/startup/exception-handlers.c:86`

### Problem

`Reset_Handler` now calls `__disable_irq()`, which sets PRIMASK.
Interrupts are re-enabled only when the Cortex-M port starts the
scheduler. Everything before that runs with all interrupts masked:
`os_startup_initialize_hardware_early()`,
`os_startup_initialize_hardware()`, the static constructors and the
first part of `main()`. Bare-metal applications that use this startup
without starting the scheduler never get interrupts.

The change was made on purpose, in its own commit (`faa8e428`,
2025-09-12, "exception_handlers.c add `__disable_irq()` in
`Reset_Handler`"), without a recorded reason.

### Scenario

On `nucleo-f411re`:

1. The board's `os_startup_initialize_hardware()` calls `HAL_Init()`,
   which starts SysTick at 1 kHz.
2. The board's `SysTick_Handler` calls `HAL_IncTick()` and
   `os_systick_handler()`.
3. With PRIMASK set, the handler never runs before the scheduler
   starts, so `uwTick` stays frozen.
4. Any `HAL_Delay()` in the hardware initialisation, in a static
   constructor or in `main()` before the scheduler starts hangs
   forever. Any HAL timeout in that window never expires.

### Documentation and tests

- The board's `initialize-hardware.c` says: "Warning: The HAL requires
  the system timer, running at 1000 Hz and calling HAL_IncTick()". The
  board was designed for the HAL tick to run from `HAL_Init()` onwards.
- The current board code (`HAL_Init()`, `SystemCoreClockUpdate()`,
  `MX_GPIO_Init()`) does not call `HAL_Delay()`, so it does not hang
  today; the problem appears as soon as the application adds one.
- The reference documents the startup order (`_start()` calls
  `os_startup_initialize_hardware_early()`, DATA/BSS initialisation,
  `os_startup_initialize_hardware()`, ..., `main()`), but neither it
  nor the user's manual says whether interrupts are enabled before
  `main()`.

### Port behaviour

- In 7.0.0, interrupts were enabled from reset until the default
  `main()` called `scheduler::initialize()`, whose Cortex-M
  implementation is `__disable_irq()`. They stayed masked until
  `port::scheduler::start()`. The change extends the masked window back
  to reset, covering the hardware initialisation and the static
  constructors.
- The core's `os_systick_handler()` updates `sysclock` and `hrclock`
  and checks their timestamps. Before the static constructors run,
  those objects are not constructed yet. A likely reason for the change
  is to keep a SysTick started early (by the HAL) from running
  `os_systick_handler()` on unconstructed clocks; that reason is not
  recorded.

### Suggested fix

Decide which startup contract is intended, and document it.

- If interrupts must stay masked until the scheduler starts, keep the
  change, document it, and update the `nucleo-f411re` board (and the
  HAL warning comment): no `HAL_Delay()` or HAL timeout may be used
  before the scheduler starts.
- If the HAL tick must run early (the board's documented design),
  re-enable interrupts after DATA/BSS initialisation (for example at
  the start of `os_startup_initialize_hardware()`, or right after
  `HAL_Init()` in the board code), and protect the RTOS side instead:
  make `os_systick_handler()` return early until `scheduler::started()`
  (the port-scheduler branch already does this for its own ISR), or
  have the board's `SysTick_Handler` call only `HAL_IncTick()` until
  then.

The second option keeps the protection without changing behaviour for
applications that need the HAL before the scheduler.

## #10 - C API default timer changed from periodic to one-shot

**File:** `src/rtos/os-c-wrapper.cpp:1511` (and line 1554 in
`os_timer_new()`)

### Problem

When `attr == NULL`, `os_timer_construct()` and `os_timer_new()` now
use `timer::once_initializer` instead of `timer::periodic_initializer`.
Existing C applications that relied on the periodic default silently
stop getting repeated callbacks, and nothing warns them at compile
time.

### Scenario

A C application expects a 1 Hz heartbeat:

```c

os_timer_start (&t, 1000);
```

After this change, `cb` runs once and never again.

- **Released behaviour:** the 7.0.0 listing shown in the reference

  version bump, and check the CMSIS RTOS validator, whose
  `osTimerCreate()` passes explicit attributes.
- **Revert to periodic**: restore `periodic_initializer` and document
  the difference from C++ in `os-c-api.h`.

## #12 - `SystemClock_Config()` runs before DATA and BSS are initialised

**File:** `src/startup/initialize-hardware.c:67`

### Problem

This was found while checking the startup sequence for #8; the original
review did not report it.

The change adds a call to `SystemClock_Config()` (when
`OS_HAS_SYSTEMCLOCK_CONFIG` is defined) in the default
`os_startup_initialize_hardware_early()`. `_start()` calls that hook
**before** copying `.data` and zeroing `.bss` (`src/startup/startup.cpp`,
around line 260).

`SystemClock_Config()` is CubeMX code built on the STM32 HAL, which
relies on initialised globals:

- `HAL_RCC_OscConfig()` and `HAL_RCC_ClockConfig()` read `uwTick`
  (`.bss`) through `HAL_GetTick()` for their timeouts;
- `HAL_RCC_ClockConfig()` writes `SystemCoreClock` (`.data`), then
  calls `HAL_InitTick(uwTickPrio)`, which reads `uwTickPrio` and
  `uwTickFreq` (both `.data`) and reprograms SysTick from them.

At that point these variables hold whatever was in RAM. Right after,
the DATA copy overwrites `SystemCoreClock` back to its initial value
(16 MHz on the F411), undoing what `HAL_RCC_ClockConfig()` computed.
The STM32 HAL also requires `HAL_Init()` to run before any other HAL
function, and on `nucleo-f411re` `HAL_Init()` only runs later, in
`os_startup_initialize_hardware()`.

### Scenario

On `nucleo-f411re`:

1. `SystemClock_Config()` switches the core to 100 MHz and sets
   `SystemCoreClock = 100000000`.
2. `HAL_InitTick()` programs SysTick using `uwTickFreq` from
   uninitialised RAM. If that value is 0, the code divides by zero,
   which faults if `SCB->CCR.DIV_0_TRP` is enabled and otherwise yields
   0.
3. The DATA copy resets `SystemCoreClock` to 16 MHz.
4. `HAL_Init()` in `os_startup_initialize_hardware()` programs SysTick
   with the stale 16 MHz value, so the HAL tick runs about 6 times too
   fast. The board calls `SystemCoreClockUpdate()` only after
   `HAL_Init()`, and nothing reprograms SysTick until the scheduler
   starts.

The board works today only because no HAL timeout or delay is used
before the scheduler reprograms SysTick, and because #8 masks the tick
anyway. A different CubeMX configuration (for example one that enables
over-drive, or uses `HAL_Delay()` in `SystemClock_Config()`) can fail
or hang.

### Documentation and tests

- The comment of `os_startup_initialize_hardware_early()` says it runs
  "right at the beginning of `_start()`" and is meant for code that
  must run before DATA/BSS initialisation (clocks, watchdog, external
  RAM). Code placed there must not depend on initialised globals,
  which CubeMX code does.
- CubeMX's own `main.c` (`tests/platforms/nucleo-f411re/stm32f411cubemx/Core/Src/main.c`)
  calls `HAL_Init()` first and `SystemClock_Config()` after it.
- `OS_HAS_SYSTEMCLOCK_CONFIG` is defined only by `nucleo-f411re`,
  which is tested manually.

### Suggested fix

Call `SystemClock_Config()` after the C runtime initialisation and
after `HAL_Init()`, in the same order as CubeMX:

- remove the call from the default
  `os_startup_initialize_hardware_early()`;
- in the board's `os_startup_initialize_hardware()`, call
  `HAL_Init()`, then `SystemClock_Config()`, then
  `SystemCoreClockUpdate()`; `HAL_RCC_ClockConfig()` then reprograms
  SysTick with the correct clock.

If early clock switching is wanted for speed, it must use only register
accesses (no HAL), and must not rely on `SystemCoreClock` surviving the
DATA copy.

## #13 - `printf()` from a timer callback fails with POSIX I/O syscalls

**File:** `src/posix-io/file-descriptors-manager.cpp:94` (also `valid()`,
`allocate()`, `deallocate()`, `socket()` and `used()`)

### Problem

The change adds, at the start of `file_descriptors_manager::io()` and
the other lookups:

```cpp
assert (!rtos::interrupts::in_handler_mode ());
rtos::scheduler::critical_section scs;
```

`__posix_write()` (`src/posix-io/c-syscalls-posix.cpp:136`) calls
`file_descriptors_manager::io(fildes)` first, even for stdout and
stderr, which fall back to `trace_write()` when no device is
registered.

The same change makes `this_thread::__errno()` return a static
`isr_errno` in handler mode, with the comment: "A timer callback runs
inside the tick ISR and a libc call there (e.g. printf) still touches
errno". So `printf()` from a timer callback is a use case the change
explicitly supports, but the new lookups reject it.

### Scenario

1. A Cortex-M application that does not define
   `OS_USE_SEMIHOSTING_SYSCALLS` (so `c-syscalls-posix.cpp` is used)
   has a timer callback that calls `printf()`.
2. The callback runs in the SysTick handler. newlib calls `_write()`,
   which calls `__posix_write(1, ...)`, which calls
   `file_descriptors_manager::io(1)`.
3. Debug builds stop at the assert. Release builds go on to
   `scheduler::critical_section`, whose Cortex-M `locked(state)` calls
   `os_assert_throw(!in_handler_mode(), EPERM)`, so they throw a system
   error, or abort when exceptions are disabled.

In 7.0.0 the same call reached `trace_write()`.

### Documentation and tests

- The `rtos-apis` timer callbacks (`tmfunc` in `test-c-api.c:75` and
  `test-cpp-api.cpp:88`) call `printf()`, which is why the `__errno()`
  change was needed.
- Every Cortex-M test platform defines `OS_USE_SEMIHOSTING_SYSCALLS`,
  whose `__posix_write()` does not use the descriptors manager, so the
  tests never take this path.
- On the native platform, `printf()` goes to the host C library, not
  to `__posix_write()`.

### Port behaviour

On Cortex-M, `port::scheduler::locked(state)` starts with
`os_assert_throw(!interrupts::in_handler_mode(), EPERM)`. A scheduler
critical section can never be taken in handler mode, in either debug or
release builds. The POSIX port has the same check, but on the native
platform `printf()` goes to the host C library, so this path is
specific to embedded builds.

### Suggested fix

Keep `io()` and `valid()` usable from handler mode: drop the assert and
use an `interrupts::critical_section` instead of a scheduler critical
section there (both only read the table). Keep the scheduler lock and
the assert in `allocate()`, `deallocate()` and `socket()`, which modify
the table and are not expected from interrupt handlers.

Alternatively, have `__posix_write()` go straight to `trace_write()` for
fd 1 and 2 when in handler mode.

## #14 - `timed_lock()` failure path recomputes the boost without a lock and sets the assigned priority

**File:** `src/rtos/os-mutex.cpp:1427`

### Problem

This bug was already present in 7.0.0 (`os-mutex.cpp:1342` on `xpack`);
it was not introduced by this change.

When `timed_lock()` times out or is interrupted on a priority-inheritance
mutex, it recomputes the owner's boosted priority from the waiting
list. It does this:

- after `internal_unlink_node()`, with **no** lock held: it reads
  `boosted_prio_`, walks `list_` and dereferences `owner_`;
- by calling `owner_->priority(boosted_prio_)`, which changes the
  owner's **assigned** priority, while every other path in the mutex
  uses `owner_->priority_inherited()`.

The change fixes a similar null `owner_` race in `internal_try_lock_()`,
but not this one.

### Scenario

1. Thread B owns an inheritance mutex and has been boosted to the
   priority of waiter A, so A and B now share a priority.
2. A's timeout expires. A wakes up and starts the recompute.
3. A tick switches to B (round-robin at equal priority), which unlocks
   the mutex. With no other waiter, `owner_` becomes `nullptr`.
4. A resumes and calls `owner_->priority(...)`: null dereference.

Without the race, the call permanently raises B's assigned priority
to the waiters' priority, which survives after B releases the mutex.

### Documentation and tests

- The reference documents `ETIMEDOUT` and `EINTR` for `timed_lock()`,
  but nothing about priority restoration on failure.
- `mutex-stress` only uses `lock()`, and `rtos-apis` calls `timed_lock(10)`
  once on an uncontended mutex (`test-cpp-api.cpp:911`), so this path
  is not exercised.

### Suggested fix

Do the recompute inside a `scheduler::critical_section`, read `owner_`
once and skip the update when it is `nullptr`, and call
`owner_->priority_inherited(max_prio)` instead of `priority()`. When no
waiters are left, also reset the inherited priority, as `unlock()` does.

## #15 - `check_timestamp()` runs `action()` outside the critical section

**File:** `src/rtos/internal/os-lists.cpp:536`

### Problem

The change splits `clock_timestamps_list::check_timestamp()`: the head
node is unlinked inside an interrupts critical section, and
`node->action()` now runs after the critical section is left. In 7.0.0
the action ran inside it. `timeout_thread_node::action()` is still
commented "Must be called in a critical section" (`os-lists.cpp:344`).

### Why this is not a bug on this branch

- `check_timestamp()` is called from the clock interrupt handlers
  (`os_systick_handler()`, the RTC handler), and from
  `clock::update_for_slept_time()`, which holds an interrupts critical
  section around it.
- On one CPU, no thread runs while an interrupt handler runs. The
  waiting thread whose stack holds the `timeout_thread_node` cannot
  return and release that stack before `action()` completes.
  `timer::stop()` and `timer::start()` cannot run from a handler either.
- Running the user's timer function outside the critical section is an
  improvement: it no longer masks interrupts for the length of the
  callback.

### Why it matters on the `smp` branch

With two CPUs, the waiting thread can be woken on the other CPU
(for example by a `post()`), find its timeout node already unlinked,
return, and reuse its stack, while the first CPU is about to call
`node->action()` on that node. A periodic timer stopped on the other
CPU can also be relinked by `timer::internal_callback()` after `stop()`
has returned.

The sibling POSIX port (SMP rewrite) and the RP2350 variant of the
Cortex-M port both run several CPUs, so this applies to them as soon as
they are used with the `smp` branch kernel. The packaged POSIX 1.0.1
used by the tests is single-CPU, and the tick handler there cannot be
interrupted by a thread, so it is not affected.

### Suggested fix

On this branch, update the comment on `timeout_thread_node::action()`
to describe the new contract.

On the `smp` branch, resume the thread (or capture what `action()`
needs) while still inside the critical section, run only the user timer
function outside it, and have `timer::internal_callback()` check
`state_` before relinking a periodic timer.
