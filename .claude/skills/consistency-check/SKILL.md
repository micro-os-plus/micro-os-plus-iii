# Consistency Check — µOS++ IIIe

## When to Use

- The user asks for a consistency check of the project, or of a part
  of it.
- After renaming files, folders, platforms, build configurations, or
  actions, to find the places left behind.
- Before a release, to find stale documentation.

This skill reports problems; it does not fix them, unless the user asks
for that separately (for example "fix #4").

Read `.github/skills/review-common.md` (the rules shared by the review
skills) and `.github/skills/project-defaults.md`, `.github/skills/project.md` first, and `project.md` in this
folder, if it exists; their rules extend these, and take precedence
where they differ.

## Scope

If the user specifies a folder, check only that folder. Otherwise check
the whole project, excluding `website/`, `node_modules/`, `xpacks/`, the
build folders (for example `build/`,
`tests/build/`), and the folders generated by vendor tools.

State the scope and the commit (`git rev-parse --short HEAD`) at the top
of the report.

## Generated and Special Files

Many files carry a `DO NOT EDIT! Automatically generated from template
file` header, naming their template (for example in
`npm-packages-helper`,
`build-helper`, or `docusaurus-template-liquid`). For each problem
in such a file, name the template that must be fixed; the generated
file is regenerated, never edited in place. When a problem is found in
a generated file, also check the template, since other projects may
share it. The other generated files are listed under "Generated Files"
in `.github/skills/project.md`.

## Checks

Read the files; do not rely on names alone. For every claim in a
README or an instruction file, verify it against the project (the file
exists, the command or action exists, the option is accepted, the
version is still used).

### 1. Functional consistency

Problems that make something fail, or would make it fail.

- **Build and test configurations** (`tests/package.json`): the
  actions, the build configurations, their `platformName` properties,
  the platform folders, and the lists of configurations used by the
  composite actions (for example `configs-ci`, `configs-boards`) must
  use the same names. Every platform must have the same set of
  per-platform actions as its siblings (for example `install-*`,
  `link-dependencies-*`, `build-*`, `test-*`, `clean-*`, `clear-*`);
  report the missing ones.
- **Build system integration**: the source files listed in
  `xcdl-package.jsonc`, `CMakeLists.txt`, and `meson.build` match the
  files in `src/`; the include folders exist.
- **Editor and debugger configurations** (for example
  `.vscode/launch.json`, `.vscode/tasks.json`): paths, build folder
  names, configuration names, and executable names match the current
  build layout.
- **CI workflows** (`.github/workflows/`): the actions and the scripts
  they invoke exist.
- **Scripts**: the paths and actions referred to by the maintenance
  and test scripts exist.

### 2. Documentation

Stale or incorrect content in:

- the top `README.md` and the READMEs in all sub-folders (for example
  tests, platforms, devices, scripts, cmake);
- `CLAUDE.md`, `.github/copilot-instructions.md`, and the skills in
  `.github/skills/`.

Look for: commands and actions that do not exist; paths, files, and
folders that were renamed or removed; descriptions of tests,
platforms, or features that no longer match; obsolete versions and
toolchains; broken links; references to other projects (copy-paste
leftovers); headings or file names with the wrong case; typos.

### 3. Names

- File and folder names follow the project conventions (lower case,
  words separated by dashes; `-inlines.h` for the inline headers) and
  are consistent between siblings (for example platforms, devices).
- File names represent their content; the `@file` `@brief` of each
  source file matches its name and content.
- Include guards match the file names.
- Each header in `include/` has its matching `inlines/` and `src/`
  files where applicable, with the same base name.
- Stray, duplicated, or unused files (for example copies in the wrong
  folder, files for obsolete toolchains, generated files nothing refers
  to).
- Identifiers in the tests and sources that were copied without being
  renamed (for example the same suite variable reused in several
  files).
- Similar items placed inconsistently (for example a file kept in one
  sibling folder only).

### 4. Verified as consistent

Also record the areas checked and found consistent, so that the next
check knows what was covered.

## Numbering

Follow "Numbering" in `.github/skills/review-common.md`, in the order of
the sections above. Each check writes a new report, numbered from `#1`.

Unlike the design review, this check reads the latest earlier report
first. Verify each of its open problems again: carry those still present
into the new report, as new items, each citing the earlier one (for
example "(CONSISTENCY-CHECK-2 #14)"), and do not carry over those fixed
meanwhile; give their count in the summary. Do not modify the earlier
report, except to mark an item `(fixed)` or `(withdrawn)` when the user
acts on it.

## Report

Write the report to the next `maintenance/docs/CONSISTENCY-CHECK-<n>.md`
file (see "Report Files" in `.github/skills/review-common.md`):

```markdown
# Consistency check

Date: <date>, on branch `<branch>`, commit `<hash>`.

Scope: <scope and exclusions>.

Earlier report: <the latest earlier report read, the number of its
problems carried over, and the number fixed meanwhile; or "none">.

Summary: <n> problems (<open> open, <fixed> fixed, <withdrawn>
withdrawn): <counts per section>.

## Note on generated files

<which problems are in generated files, and which templates to fix>

## 1. Functional consistency

- **#1 — <short title>.** <description, with file and line references,
  why it matters, and the template to fix, if generated>
- **#2 — <short title>.** (CONSISTENCY-CHECK-1 #5) <description of a
  problem carried over from the earlier report>.

## 2. Documentation

### `<file>`

- **#3 — <short title>.** <description>

## 3. Names

- **#4 — <short title>.** <description>

## 4. Verified as consistent

- <area checked and found consistent>

## 5. Proposed next steps

- <grouped, actionable steps, referring to the problem numbers>
```

Each item states the problem directly and specifically: the file, the
line or the setting, what is wrong, and what is expected. When unsure
whether something is a problem or a deliberate choice (for example a
platform intentionally left out of a list), say so in the item, and ask
the user in the summary rather than guessing.

## Procedure

1. Determine the scope, and the number of the new report; read the
   latest earlier report, if any.
2. List the files in scope, and read the configuration files, the
   READMEs, and the instruction files fully.
3. Go through the checks section by section, verifying each finding in
   the files (and in the templates, for generated files), and verify
   again the open problems of the earlier report.
4. Number the findings as described above, check the numbering, and
   write the report.
5. Give the user a short summary: the counts, the most serious
   problems by number, and the questions that need a decision.
6. Do not fix anything unless asked; when the user later refers to a
   number, follow "Acting on an Item" in
   `.github/skills/review-common.md`, and mark the item in the report
   that lists it.
